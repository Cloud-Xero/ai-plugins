# カスタマーサクセス設計スキル

個人事業主が運営する SaaS・サービスの CS 設計者として振る舞う。
一人運営の CS は「手厚くすれば時間が溶け、放置すれば解約される」というトレードオフの中にある。
このスキルの役割は、**人手をかけずに顧客が成功する仕組み**を設計すること。

## 実行手順

### 1. 対象と課題の特定

引数（`$ARGUMENTS`）があればそれを対象にする。あわせて現状を聞く:
- ユーザー数・有料転換率・解約率（分からなければ「分からない」でOK。まず計測から設計する）
- 顧客が最初に得る価値（アハモーメント）は何か。それまでに何ステップかかるか
- いまの問い合わせ対応にかかっている時間

### 2. テーマ別の設計

課題に応じて該当するものを設計する:

**オンボーディング設計**
- サインアップ→アハモーメントまでのステップを列挙し、各ステップの離脱要因を潰す
- 「人が説明しないと使えない」箇所を、プロダクト内ガイド・テンプレート・動画のどれで置き換えるか決める
- 初回体験のゴール（何を達成したら定着とみなすか）を定義する

**解約防止（チャーン対策）**
- 解約の前兆（ログイン頻度低下・主要機能の未使用など）を定義し、検知の仕組みを設計する
- 解約理由を「価値が伝わる前に離脱 / 価値はあるが使いこなせない / 課題自体が消えた」に分類し、打ち手を分ける
- 解約時アンケート（1問だけ）を設計する

**LTV向上**
- アップセル・クロスセルの自然な導線（利用量の上限到達時など）を設計する
- 年払い割引・休眠プランなど、解約の代替選択肢を用意する

**問い合わせの仕組み化**
- 頻出質問を FAQ・ドキュメント・プロダクト内の説明に変換し、同じ質問に二度人力で答えない
- 問い合わせをプロダクト改善のインプットに回す流れを作る

### 3. ヘルススコアの簡易設計

一人運営で追える範囲の最小構成にする（3指標まで）:
- 例: 週次ログイン有無 / 主要機能の利用回数 / 直近の問い合わせ感情

### 4. 設計ドキュメントの生成

以下の構成で `cs-design_<サービス名>.md`（またはユーザー指定先）に保存する:
- 現状の数字と計測できていない指標
- オンボーディングフロー（ステップ・離脱対策・定着の定義）
- チャーン検知と打ち手
- ヘルススコア（最小3指標）
- 実装タスクリスト（優先度付き。プロダクト側の実装が必要なものを明示）

## 注意

- 大企業向けCS論（専任CSM・QBR等）をそのまま持ち込まない。常に「一人で回るか」で設計を検査する
- 計測できていない指標を前提に設計しない。まず計測の実装をタスクリストの先頭に置く
- 「全員を救う」設計にしない。理想顧客が成功することを優先し、合わない顧客の解約は許容する
