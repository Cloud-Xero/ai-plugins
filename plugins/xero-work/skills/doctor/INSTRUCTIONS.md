# Mac が重い原因を診断する

「Macが重い」に対して、**推測ではなく実測で原因を名指しする**ための手順書。

## 絶対原則

1. **対処法を答えにしない。** 「再起動してください」は対処であって原因ではない。原因を聞かれているのに対処を繰り返すと、ユーザーは「質問に答えていない」と受け取る。原因を確定させてから対処を述べる。
2. **相関を因果と言わない。** 「今日インストールされたソフトがある」は状況証拠にすぎない。実測で裏が取れるまで犯人扱いしない。一度否定された容疑者を、あとの説明で蒸し返さない。
3. **特定できないことは、早い段階で「できない」と言う。** 特に蓄積型の問題は、過去の記録が残っていないため原因プロセスの特定が原理的に不可能なことがある。可能性を匂わせてコマンドを投げ続けるより、限界を先に宣言するほうが誠実。
4. **ユーザーの証言と OS の記録が食い違ったら、記録を複数の独立ソースで裏取りしてから提示する。** 証言を頭ごなしに否定しない。「操作はしたが完了していない」など、両方が正しくなる説明を探す。
5. **重篤な状態のマシンで設定変更をしない。** メモリ枯渇中は各種デーモンが応答せず、設定が中途半端に壊れる。まず状態を回復させてから設定を触る。

## Phase 0 — 一次計測（sudo 不要・必ず最初に実行）

```bash
# 1. 全体像
uptime
sysctl -n machdep.cpu.brand_string hw.memsize hw.ncpu
sw_vers

# 2. メモリとスワップ（最重要）
top -l 1 -n 0 | grep -E "PhysMem|VM:|Load Avg|CPU usage"
sysctl vm.swapusage

# 3. プロセス上位
ps -Aceo pid,pcpu,pmem,comm -r | head -15    # CPU順
ps -Aceo pid,pmem,rss,comm -m | head -15     # メモリ順

# 4. ディスクとサーマル
df -h / /System/Volumes/Data
pmset -g therm
```

`top` の出力例と読み方:

```
PhysMem: 17G used (12G wired, 3406M compressor), 64M unused
VM: ... 603745449(603) swapins, 621380536(0) swapouts
CPU usage: 4.20% user, 7.84% sys, 87.95% idle
```

- `wired` — カーネル・ドライバが確保しスワップ不可の領域。**この値が全体の判断を左右する**
- `unused` — 空き。数百MB以下なら枯渇
- `swapins` の**括弧内**が現在進行中の回数。**0以外ならスワップ継続中＝スラッシング**
- `idle` が高いのに重い ＝ CPU 原因ではない。**I/O 待ち**

## Phase 1 — 型の判定

Phase 0 の結果を下表に当てて、**該当する型だけ** Phase 2 に進む。全部やらない。

| 判定 | 条件 | 進む先 |
|---|---|---|
| **メモリ型** | `unused` が数百MB以下 / スワップ使用中 / swapins括弧内が0以外 | Phase 2-A |
| **CPU型** | `idle` が低い（<50%）／特定プロセスが継続的に高CPU | Phase 2-B |
| **ディスク型** | 空き容量が10%未満 | Phase 2-C |
| **サーマル型** | `pmset -g therm` に警告あり | Phase 2-D |
| **判定不能** | 上記いずれも該当しない | Phase 2-E |

**CPU が idle なのに重い場合、原因は必ず「待ち」である。**メモリ型かディスク型を疑う。

## Phase 2-A — メモリ型の深掘り

### A-1. wired の量で分岐

```bash
top -l 1 -n 0 | grep PhysMem
```

- **wired が 2〜4GB 程度** → 正常。アプリのメモリ使用量が原因。A-3 へ
- **wired が 6GB 以上** → 異常。カーネル側のリークを疑う。A-2 へ

### A-2. カーネルゾーンの内訳（要 sudo・ユーザーに実行を依頼）

ユーザーに以下を実行してもらう。**`sudo` はこちらから実行できないため、コマンドを提示して結果を貼ってもらう。**

```bash
sudo zprint -t | sort -k5 -rn | head -20
```

出力の1〜2位が突出していれば、それがリーク元のゾーン。次にタグ（呼び出し元サブシステム）を特定する。ゾーン名が `data.kalloc.NNNN` のように汎用アロケータだった場合は、必ずタグまで追う。

```bash
sudo zprint -t | grep "<ゾーン名>"
```

`ゾーン名[タグ]` の形式で出る。**角括弧の中が確保したサブシステム**。

代表的なタグの読み方:

| タグ | 意味 | 主な発生源 |
|---|---|---|
| `vfs.namei` | ファイルパス名の解決バッファ | Spotlight索引、大量のファイル走査 |
| `VM.map.entries` | メモリマッピング管理 | mmap を多用するプロセス |
| `compressor_*` | 圧縮メモリ | メモリ枯渇の結果（原因ではない） |
| `vnodes` / `APFS_INODES` | ファイルシステムのキャッシュ | 通常は正常 |

**注意**: `zprint` の出力は末尾にタグ集計セクションがある。`head` だけ見ると見落とす。ゾーン名が分かっているなら `grep` で直接引く。

### A-3. リーク速度の実測（結論を裏付ける）

**10〜20分あけて2回計測し、増加量を測る。**これで「進行中か」「1日あたり何MBか」が定量化でき、「なぜ昨日は平気で今日ダメなのか」に数字で答えられる。

```bash
# 1回目と2回目の該当ゾーンのサイズを比較
sudo zprint -t | grep "<ゾーン名>"
```

### A-4. 引き金プロセスの特定（限界を理解した上で）

```bash
sudo fs_usage -w -f filesys | grep -viE "PgOut|PgIn|PAGE_" | head -3000 \
  | awk '{print $NF}' | sed 's/\.[0-9a-fx]*$//' | sort | uniq -c | sort -rn | head -20
```

**`PgOut|PgIn|PAGE_` の除外は必須。**除外しないと `kernel_task` のスワップ書き込みが出力の9割を占め、判定を誤る（`kernel_task` が1位なら、それはスワップのノイズであって原因ではない）。

**この計測の限界を必ず先に伝えること:**
- 出るのは「今アクセスが多いプロセス」であり、数十日かけて蓄積した分の犯人ではない
- カーネル側のバグなら、普通にファイルを開いただけのプロセスも踏む
- 一過性のプロセスが上位に来ることがある。**15秒ほど張り込んで再現しなければノイズと判断する**

```bash
# 上位に出たプロセスが常駐しているかの確認（自分で実行可能）
end=$((SECONDS+15))
while [ $SECONDS -lt $end ]; do ps -Aeo pid,ppid,comm= | awk '$3=="<名前>"{print $1,$2}'; done | sort -u
```

## Phase 2-B — CPU型の深掘り

```bash
# 実測（1回目のサンプルは無意味なので3回取って3回目を見る）
top -l 3 -n 12 -o cpu -stats pid,cpu,mem,time,command | awk '/^Processes/{n++} n==3'

# 累積CPU時間の上位（じわじわ食っている常駐を炙り出す）
ps -Aceo time,pcpu,rss,etime,pid,comm | sort -k1 -r | head -20
```

`%CPU` の瞬間値だけでなく**累積時間（TIME）と経過時間（ELAPSED）の比**を見る。経過に対して累積が大きいものが慢性的な負荷源。

`kernel_task` が高い場合はサーマルスロットリング（Phase 2-D）かドライバの問題を疑う。

## Phase 2-C — ディスク型の深掘り

```bash
df -h /System/Volumes/Data
sudo du -sh /* 2>/dev/null | sort -h | tail -15
```

空き容量が枯渇するとスワップ領域も確保できず、メモリ型の症状を併発する。またSpotlight索引・スワップファイル・スリープイメージが数十GB単位を占めることがある。

## Phase 2-D — サーマル型の深掘り

```bash
pmset -g therm
sudo powermetrics -n 1 -i 1000 --samplers smc,cpu_power 2>/dev/null | head -30
```

`CPU_Speed_Limit` が100未満ならスロットリング中。物理的要因（通気・外部ディスプレイ・充電）を確認する。

## Phase 2-E — 判定不能のとき

常駐プロセスとプロセス総数を確認する。

```bash
ps -Ac | wc -l
ps -Aeo etime,pid,pcpu,rss,comm | sort -k1 -r | head -20   # 長期稼働の常駐
systemextensionsctl list                                     # サードパーティのシステム拡張
kextstat | grep -v com.apple                                 # サードパーティkext
netstat -m | head -12                                        # ネットワークバッファ
sysctl kern.num_files kern.maxfiles                          # ファイルディスクリプタ
```

## Phase 3 — 報告

必ずこの順で述べる。

1. **原因**（何が、どれだけ、どういう機序で遅くしているか）
2. **根拠**（実測値。推測と実測を明確に区別する）
3. **シロだったもの**（ユーザーが疑っていた対象を実測で除外できたなら明示する）
4. **特定できなかったこと**とその理由
5. **対処**（最後）

### 「なぜ急に重くなったのか」への答え方

蓄積型の問題では、ユーザーは必ず「蓄積なら徐々に重くなるはずだ」と指摘してくる。これは正当な指摘であり、以下で答える。

> **蓄積は線形だが、体感は階段。**空きメモリが残っている限り体感はゼロ。使い切った瞬間にスワップに落ち、スワップはメモリの1000倍以上遅いため、ある日を境に突然崩れる。さらにスラッシング（追い出す→すぐ必要になる→また追い出す）は自己増悪するので、閾値を越えた後の悪化は急激になる。

リーク速度を実測していれば「昨日との差は N MB でしかない」と数字で示せる。**A-3 の2回計測をやっておくこと。**

## 既知の罠（実際に踏んだもの）

| 罠 | 正しい扱い |
|---|---|
| `top` の MEM 列と `ps` の RSS が食い違う | 別指標。共有ライブラリを含むかが違う。**実占有は `ps` の RSS** で判断する |
| `vm_stat` のページサイズを 4096 と仮定 | **Apple Silicon は 16384**。`vm_stat` の1行目に明記されている。必ず読む |
| `fs_usage` で `kernel_task` が1位 | スワップの `PAGE_OUT` ノイズ。除外して取り直す |
| プロセスが大量に起動している（例: 同名プロセスが十数個） | **合計 RSS を計算してから判断する**。数が多くても合計が数百MBなら主因ではない |
| インストール履歴とトラブル発生日が一致 | 状況証拠。実測の裏付けなしに犯人としない。**ユーザーが「その前から」と言ったら即座に除外し、以後蒸し返さない** |
| ユーザーが「再起動した」と言うが uptime が長い | `kern.boottime` / `last reboot` / **`ps -p 1 -o lstart,etime`（launchd）** の3点で裏取り。launchd はブート時にしか生成されないため決定的。「再起動を実行したが、アプリの終了確認で止まって完了しなかった」可能性を提示する |
| メモリ枯渇中に `mdutil` などで設定変更 | **やらない。**デーモンが応答せず `-405 / unknown indexing state` で状態が壊れ、索引の再構築が始まって事態が悪化する。回復後に実施する |
| `sudo` コマンドを実行できずパスワード要求で止まる | Bash ツールからは `sudo` を対話実行できない。**ユーザーに `!` プレフィックスでの実行を依頼する**か、ターミナル.app での実行を案内する |
| 出力が長いコマンドに `head` を付けて重要部分を切り落とす | 目的の情報がどこにあるか（先頭か末尾か）を確認してからフィルタする。分かっているなら `grep` で直接引く |

## 対処の指針

| 原因 | 対処 |
|---|---|
| wired のカーネルリーク | **再起動のみ。**アプリ終了やメモリ解放ツールでは一切解放されない |
| スワップ枯渇 | 再起動（スワップファイルも削除される） |
| 特定プロセスの暴走 | そのプロセスの終了・再起動 |
| ディスク枯渇 | 不要ファイル削除、Spotlight索引の削除 |
| namei リークの再発抑制 | Spotlight索引を無効化（下記）。ただし**必ず正常な状態で実施する** |

### Spotlight の無効化（Raycast等の代替がある場合）

```bash
sudo mdutil -i off /System/Volumes/Data    # 索引停止（ボリューム指定が必須）
sudo mdutil -X /System/Volumes/Data        # 索引データ削除（-X はパス必須。-a と併用不可）
mdutil -s -a                               # 確認（全ボリュームが disabled になっていること）
```

影響: ⌘スペース検索、Finder検索、メール等のアプリ内検索、Raycastの File Search が使えなくなる。アプリ起動やクリップボード履歴など Raycast の他機能には影響しない。

### 再起動を案内するときの注意

- **前回の再起動が完了していなかった形跡がある場合**、原因はアプリの終了確認ダイアログでのブロック。ブラウザ等を先に ⌘Q で閉じてから実行し、Appleロゴが出るまで見届けるよう伝える
- 「再度ログインしたときにウインドウを再度開く」のチェックは外すことを勧める。ただし**アプリ自身の復元機能（ブラウザのタブ復元、ターミナルマルチプレクサのセッション復元）は別物で失われない**ことも併せて伝える。これを説明しないとユーザーは作業が失われると誤解する

## 再発防止の運用

- カーネルのリークは OS 側の欠陥であり、根治はアップデート待ち
- 実測したリーク速度から、閾値到達までの日数を概算して再起動の周期を提案する
  （例: 127MB/日で残り6GB → 約47日 → 月1回の再起動で十分）
