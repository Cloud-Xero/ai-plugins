# Refactor Page（オーケストレータ）

`docs/refactoring/` のリファクタリング計画（`refactor-plan` スキルが生成する形式）から、**残っている PR ステップを全て**実装し、**ステップごとに 1 PR**（stacked PR）を作成する。
**このスキルはコードを書かない。** 計画の解決・進捗判定・ブランチ命名・PR 作成・**リポジトリ事実の収集**だけを行い、実装と検証はサブエージェントに委譲するオーケストレータに徹する。
worktree 隔離で動くため、実行中もユーザーのメイン checkout には触れない。ブランチ作成と PR 作成はこのスキルの契約に含まれるため、実行ごとの確認は不要。

このスキルは特定プロジェクトに依存しない。**プロジェクト固有の情報（検証コマンド・規約・PR テンプレート等）はすべて工程 0 で収集し、エージェントへのプロンプトで毎回渡す**。エージェント定義側には書かれていない前提。

## 原則

- **1 回の実行 = 計画の残り全 PR ステップ = ステップ数ぶんの PR**。1 PR ステップを 1 PR にまとめる粒度は崩さない（計画の「挙動不変・独立マージ可能」の原則を維持）
- **stacked PR**: PR N の base は PR N-1 のブランチ。最初に実施するステップの base だけがデフォルトブランチ
  - GitHub は base ブランチがマージされると子 PR の base を自動で付け替えるため、**ユーザーは番号順にマージするだけでよい**
  - 各 PR の diff がそのステップの変更だけになり、レビュー単位が保たれる
- ステップは**必ず直列**に実行する（PR N の実装は PR N-1 の成果物に依存する）
- マージはしない（ユーザーの判断）
- 途中のステップで検証が通らなければ**そこで打ち切る**。それまでに作成した PR は残す

## 使うサブエージェント

| エージェント | 役割 | 呼び方 |
|---|---|---|
| `refactor-implementer` | PR ステップ 1 つを実装→検証コマンド→コミット→push | `isolation: "worktree"`, `run_in_background: false` |
| `refactor-verifier` | push 済みブランチを挙動不変の観点で検証（PASS/FAIL） | 同上、implementer の直後 |

subagent_type は環境の一覧に出ている名前で指定する（プラグイン経由なら `xero-work:refactor-implementer` のように名前空間付きの場合がある。同名のプロジェクトローカル版が併存するリポジトリでは、**どちらを使うかを起動前に確認**し、混在させない）。
依存関係があるため必ず**順番に**実行する。1 ステップにつき implementer → verifier の 1 セット。

## 入力

- 引数: 計画名（例: `lists`）またはパス（例: `docs/refactoring/lists.md`）
  - `lists PR 3` のようにステップ番号を明示 → **そのステップ 1 つだけ**実行する（単発モード）
  - `lists from 3` → PR 3 以降の残り全部
  - 番号指定なし → 未実施ステップを**全て**実行する（デフォルト）
- 引数なし → `docs/refactoring/README.md` の計画一覧（優先度順）を読み、AskUserQuestion で対象計画を 1 回だけ聞く。候補には規模・主な問題を添える。README も無ければ `docs/refactoring/*.md` を列挙する

## オーケストレータの手順

### 0. リポジトリ事実の収集（エージェントに渡す材料）

計画に着手する前に、以下を**実測**して「リポジトリ事実」としてまとめる。これを工程 4・5 のプロンプトに毎回丸ごと渡す。

1. **パッケージマネージャとインストールコマンド**: lockfile で判定（`pnpm-lock.yaml` → `pnpm install --prefer-offline`、`package-lock.json` → `npm ci`、`yarn.lock` → `yarn --frozen-lockfile` 等）。worktree は node_modules を持たないため必須
2. **検証コマンド**: `package.json`（monorepo ならルート + 対象ワークスペース）の scripts から lint / typecheck / test / build の**実コマンド名**を特定する（例: `pnpm -C apps/web lint`）。scripts に無いものは「なし」と明記する
3. **worktree で実行できない検証**: build 等が worktree で失敗する要因（復号鍵が必要な暗号化 env、ローカル限定の secret、外部サービス依存）がないかを確認する。判断できない場合は最初のステップで一度だけ実測し、失敗するなら「理由 + CI に委ねる」を事実に含めて PR 本文にもその旨を書く
4. **プロジェクト規約・制約**: プロジェクトの `CLAUDE.md`（と読み込まれているメモリ）から、実装時に抵触しうる禁止事項・必須パターンを抜き出して制約リストにする。計画ファイルの「リスクと注意点」節と重複してよい（両方渡す）
5. **PR の作法**: `.github/pull_request_template.md` の有無とパス、PR 本文の言語（テンプレートや既存 PR に倣う。判断できなければ日本語）、コミット規約（Conventional Commits が既定）
6. **デフォルトブランチ名**: `git remote show origin` 等で確認する（`main` 決め打ちにしない）

### 1. 計画の解決と読み込み

`docs/refactoring/<name>.md` を解決して**全文**読む。「実行ステップ（PR 単位）」の**全ステップ**と各完了基準、前提（テスト基盤の要否）を把握する。

計画によってステップの見出し記法は揺れる（`### PR 2 — ...` / `### PR-2: ...` / `- **PR 2 — ...**` の箇条書き）。見出しレベルに依存せず本文から列挙すること。「任意」「スコープ外の提案として起票のみ」と明記されたステップは**既定では実行しない**（実行対象から外した旨を報告する。ユーザーが明示指定した場合のみ実行）。計画が親計画ドキュメントを参照していればそのパスも控える。

### 2. 進捗判定 — 残ステップのリストを作る

以下を突き合わせて、実施済み / 未実施を判定する:

1. **コードベースの現状**: 計画の「目標構造」のファイル群（`types.ts`、`lib/`、`hooks/`、`components/`、テストファイル）を Glob で確認し、各ステップの完了基準（成果物ファイルの存在・`wc -l` の行数）と照合する
2. **既存 PR / ブランチ**: `gh pr list --state all --search "refactor/<name>"` と `git ls-remote --heads origin "refactor/<name>*"` を確認する
   - **open PR がある** → そのステップは実装済み。**その PR のブランチを次ステップの base にして続きから積む**（stacked なので未マージでも次に進める。これが単発モードとの最大の違い）
   - push 済みブランチだけあり PR が無い → 中断残骸の可能性。状態を報告し AskUserQuestion で「続きから PR 作成 / 破棄してやり直し」を確認する
   - マージ済み PR がある → そのステップは完了。base の起点をデフォルトブランチに戻せる
3. **テスト基盤**: テストランナー設定・setup ファイル・モックヘルパーの有無を確認する。未整備で最初のステップが PR1（characterization テスト）なら、計画の前提どおり「基盤導入も含める」ことを implementer への指示に明記する

全ステップ完了済みで**計画ファイルがまだ残っている**場合は、実装は行わず「計画ファイルの削除」（下記）だけの後始末 PR を作る。計画ファイルも削除済みなら、何もすることがない旨を報告して**止める**（無理に作業をひねり出さない）。

**実行計画（残ステップの一覧・各ステップのブランチ名と base・想定 PR 数）をユーザーに提示してから着手する。** 承認待ちはしない（PR 作成まではスキルの契約）が、何本の PR が生成されるかを事前に見せる。

### 3. ブランチ名と base を決める

- ブランチ名: `refactor/<name>-pr<N>-<内容の英語 kebab-case>`（例: `refactor/lists-pr2-extract-types`）。手順 2 で確認した既存ブランチと衝突しないこと
- base:
  - 最初に実施するステップ → 直前の実施済みステップのブランチ（open PR がある場合）。無ければデフォルトブランチ
  - 2 つ目以降 → **直前のステップのブランチ**

### 4〜6 をステップごとに繰り返す

残ステップを番号順に、以下の 4 → 5 → 6 を 1 ステップずつ回す。**次のステップに進む前に、そのステップの PR 作成まで終わらせる**（implementer が base ブランチを origin から fetch する必要があるため、push 済みであることが前提）。

### 4. 実装 — `refactor-implementer`

`isolation: "worktree"`、`run_in_background: false` で呼ぶ。プロンプトに必ず渡す:

- `plan`: 計画ファイルパス（親計画があればそのパスも）
- `step`: PR ステップ番号と見出し（計画の該当節をそのまま引用してよい）
- `branch`: 手順 3 のブランチ名
- `base`: 分岐元ブランチ（デフォルトブランチ、または直前ステップのブランチ）
- `mode: new`
- **リポジトリ事実**（工程 0 の全項目: インストールコマンド / 検証コマンド / 実行しない検証とその理由 / 制約リスト / コミット規約）
- テスト基盤の整備状況（手順 2-3 の結果）と、進捗判定で気付いた計画と実コードの乖離
- **前ステップの成果**（このステップが依存するもの）: 前ステップで実際に作られたファイル・関数名・型名。計画の記述と実装がずれた場合、後続ステップは**実装された方**に合わせる必要がある。implementer が報告した「計画との乖離」をここに引き継ぐ
- **最終ステップの場合**: `cleanup` 指示（下記「計画ファイルの削除」の内容）を添える。計画自体の最終 PR に「本計画書の削除」が書かれている場合も、具体的な削除対象はこの指示で確定させる

### 計画ファイルの削除（最終ステップの PR に含める）

refactoring フォルダは全計画の消化とともに**空にする**のがゴール。対象計画の**最後の PR ステップ**を実施するときは、implementer への指示に以下を含め、同じ PR で削除させる:

- `docs/refactoring/<name>.md` を削除する
- `docs/refactoring/README.md` の計画一覧テーブルから該当行を削除する（「横断的な発見」に該当計画への参照があればそれも整理する）
- 削除するのが**最後に残った計画ファイル**なら、`README.md` も削除して refactoring フォルダを空にする
- コミットは実装分と分けてよい（`docs(refactoring): remove completed <name> plan`）

手順 2 で「全ステップ完了済みだが計画ファイルが残っている」と判定した場合は、この削除だけを行う後始末 PR（ブランチ名 `refactor/<name>-cleanup-plan`）を implementer に作らせる。

### 5. 検証 — `refactor-verifier`

implementer が push した `branch` と `base`・`plan`・`step`・**リポジトリ事実**を渡して `refactor-verifier` を同じく worktree 隔離で呼ぶ。**`base` を必ず渡すこと**（stacked ではデフォルトブランチとの diff は前ステップの変更を含んでしまい、スコープ判定が誤る）。最終ステップで計画ファイルの削除を指示した場合は、その削除が**スコープ内**である旨を verifier にも伝える。

- **PASS** → 手順 6 へ
- **FAIL** → 指摘リストを `mode: fix` で `refactor-implementer` に渡して再実行 → 再度 verifier。**最大 2 往復**。それでも FAIL なら**そのステップの PR は作らず、残りのステップも実行せずに打ち切る**。ブランチ名・残指摘・経緯と、それまでに作成済みの PR 一覧を報告してユーザーの判断を仰ぐ

### 6. PR 作成

メイン checkout から `gh pr create --base <base> --head <branch>` で作成する（checkout の branch は切り替えない。**`--base` はデフォルトブランチ固定ではなく手順 3 の base**）:

- タイトル: コミットと同じ Conventional Commits 形式（例: `refactor(lists): extract types and pure functions (PR 2/10)`）
- 本文: PR テンプレート（工程 0 で確認したもの）があればそれに従い、無ければ 概要 / 変更内容 / テスト計画 の構成で、工程 0 で決めた言語で書く
  - 概要: 計画ファイルへのリンク（`docs/refactoring/<name>.md`）と対象 PR ステップ、挙動不変である旨
  - **stacked PR の明示**: base がデフォルトブランチでない場合、「この PR は #<前 PR 番号> の上に積まれています。先に #<前 PR 番号> をマージしてください（マージ後 base は自動で付け替わります）」を概要の冒頭に書く
  - テスト計画: 実行済みの検証コマンドはチェック済み、worktree で実行できなかった検証（build 等）は**未チェックとし理由と「CI に委ねる」旨を明記**
  - 末尾: `🤖 Generated with [Claude Code](https://claude.com/claude-code)`

PR 作成後、**そのステップの完了を 1〜2 行でユーザーに報告してから次のステップに進む**（全ステップぶん黙って走らない）。

### 7. 報告（全ステップ終了後にオーケストレータがまとめる）

- 進捗判定の要約（何を実施済みと判定し、どのステップを実行したか。除外した「任意」ステップがあればそれも）
- **作成した PR の一覧**（番号順に PR URL・タイトル・base・変更ファイル数）とマージ順の指示
- 各ステップの検証結果（verifier の判定・FAIL→fix の往復があればその内容）
- implementer が報告した「スコープ外で発見した問題」（重複を除いて別 PR 候補として列挙）
- 打ち切った場合: どのステップで止まったか・残指摘・未実行のステップ
- 完走した場合: 計画ファイルを削除したこと、refactoring フォルダの残り計画数
- **ユーザーがやること**: PR を**番号順に**レビュー → CI（worktree で実行できなかった検証含む）確認 → マージ。順序を守れば base は自動で付け替わる

## オーケストレータが自分でやらないこと

- コードの実装・修正（implementer の仕事）。verifier の指摘を自分で直さない
- メイン checkout での branch 切替・checkout の変更
- PR のマージ、1 ステップを複数 PR に割ること / 複数ステップを 1 PR にまとめること
- 計画ファイル（docs/refactoring/）の書き換え
