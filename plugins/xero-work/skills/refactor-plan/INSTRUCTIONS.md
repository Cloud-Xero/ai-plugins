# refactor-plan

肥大化したページ・feature・モジュールを **挙動不変のまま** 段階的に解体するための計画書を作るスキル。
2 つの専用エージェントを対象ごとにパイプライン起動し、`docs/refactoring/<対象>.md` を出力する。

**このスキルはコードを 1 行も書き換えない。** 出力するのは計画書（Markdown）だけ。計画の実行（実装・PR 作成）は別スキル（`refactor-page` 等）の領分。

## パイプライン全体像

| 工程 | 担当 | 入力 | 出力 |
|---|---|---|---|
| 0. 対象決定・前提収集 | スキル本体 | ユーザー指定 / `wc -l` ランキング | 対象リスト・制約リスト |
| 1. 実測と構造分析 | `refactor-plan-analyzer`（対象ごとに並列） | 対象パス・制約リスト | `<一時ディレクトリ>/<対象>-analysis.md` |
| 2. 計画書の執筆 | `refactor-plan-writer`（対象ごと） | 1 の分析 + テンプレ | `docs/refactoring/<対象>.md` |
| 3. 索引の更新 | スキル本体 | 2 の成果物 | `docs/refactoring/README.md` |

対象が複数あるときは、対象間に依存がないので **対象ごとに独立したパイプライン**として回してよい（analyzer をまとめて並列起動 → 終わったものから writer を起動）。工程 1 → 2 は同一対象内では必ず直列。

## 貫くべき原則（計画書に必ず反映させる）

- **全 PR 挙動不変**。UX 改善・仕様変更・バグ修正を混ぜない。気づいた問題は「別 PR で提案」として記録するだけ
- **1 PR = 1 つの構造変更**。各 PR は単独でマージ可能
- **抽出順序は 型 → 純関数 → カスタムフック → プレゼンテーション部品**。下層から順に固める
- **PR1 は必ず安全網**（characterization テスト）。テスト基盤が未導入ならその導入も PR1 に含める。以降の全 PR はこのテストが緑であることをマージ条件にする
- **数字は実測のみ**。行数・フック回数・重複箇所は必ずコマンド出力から取る。「およそ〜行と思われる」は書かない
- **スコープ外を明記する**。やらないこと（状態管理ライブラリ導入、Server/Client 境界の見直し、DB 変更 等）を節に書く

## 手順

### 0. 対象決定と前提収集

1. **対象の特定**
   - 引数で対象が渡されていればそれを使う（例 `/refactor-plan /lists`、`/refactor-plan features/mandala`）
   - 渡されていなければ実測で候補を出す。リポジトリのソースディレクトリに対して行数ランキングを取り、上位を提示してどれを計画化するかユーザーに選ばせる（複数選択可）

     ```bash
     find <src-root> \( -name node_modules -o -name .next -o -name dist -o -name .git \) -prune -o \
       -type f \( -name '*.tsx' -o -name '*.ts' \) -print | xargs wc -l | sort -rn | head -30
     ```
   - 「ページ単位」で切るのが基本。1 ファイルが巨大なら 1 ファイル = 1 計画、小さいファイル群の重複が問題なら「公開静的ページ群」のようにまとめて 1 計画にする

2. **出力先の決定**: 既定は `<repo-root>/docs/refactoring/`。既に同名の計画書がある場合は上書きしてよいかユーザーに確認する

3. **前提の収集**（ここを省くと計画書が一般論になる）。以下を読み、**制約リスト**として writer に渡す文面にまとめる
   - `CLAUDE.md`（プロジェクト直下・親ディレクトリ・ユーザーグローバル）の禁止事項・命名規約・技術制約
   - プロジェクトメモリ（`MEMORY.md` とその参照先）の feedback / incident。過去に踏んだ地雷は計画書の「リスク」節に必ず載せる
   - 親計画にあたるドキュメント（`docs/*refactoring*` 等）があればそのパスと Phase 定義
   - **テスト基盤の現状**: テストランナーの設定ファイル、RTL 等の devDependencies、setup ファイル、既存テストの本数。PR1 の内容がここで変わる（未導入なら導入込み、導入済みなら characterization テストのみ）
   - `package.json` の scripts（lint / typecheck / test / build のコマンド名）。完了基準に実コマンド名で書くため

4. ここまでを 3〜5 行でユーザーに報告してから工程 1 に進む

### 1. refactor-plan-analyzer の起動（対象ごとに並列）

Agent ツールで `subagent_type: refactor-plan-analyzer` を起動する。対象が複数なら**同一メッセージで並列起動**する。プロンプトに必ず含めるもの:

- 対象の名前（出力ファイル名になる。例 `lists` / `mandala` / `public-pages`）
- 対象に含まれるパス（ディレクトリまたはファイル群）の**絶対パス**
- リポジトリルートの絶対パス
- 分析の出力先: `<一時ディレクトリ>/<対象>-analysis.md` の絶対パス。一時ディレクトリはセッションの scratchpad（あれば）、なければ `mktemp -d` で作る。**対象リポジトリの中には置かない**（中間物がコミットされるのを防ぐ）
- 工程 0 で集めた制約リスト（CLAUDE.md・メモリ由来）とテスト基盤の現状
- 「コードは変更しない。読むだけ」の明示

完了報告（規模・重複件数・警告）を対象ごとに 1〜2 行でユーザーに中間報告する。

### 2. refactor-plan-writer の起動（対象ごと）

analyzer の完了を確認したら、同じ対象について `subagent_type: refactor-plan-writer` を起動する。プロンプトに必ず含めるもの:

- 分析ファイル（工程 1 の出力）の**絶対パス**
- 計画書の出力先 `<出力先>/<対象>.md` の**絶対パス**
- **テンプレートの絶対パス**: `${CLAUDE_PLUGIN_ROOT}/skills/refactor-plan/plan-template.md`。環境変数が解決できない場合は、プラグインの実体はカレントリポジトリではなく **`~/.claude/plugins/` 配下のキャッシュ**にあるため、`Glob` で `~/.claude/plugins/**/skills/refactor-plan/plan-template.md` を引いて実パスを渡す（対象リポジトリ内を探しても見つからない）
- 親計画のパス（あれば）と、そこでの位置づけ（Phase N）
- 制約リストと、lint / typecheck / test / build の実コマンド名
- ユーザーが追加で指定した方針（目標行数、優先度、期限感、やらないこと）があれば添える

複数対象を回す場合、analyzer が終わった対象から順に writer を起動してよい（全 analyzer の完了を待つ必要はない）。

### 3. 索引の更新

全計画書が出揃ったら `<出力先>/README.md` を作成または更新する。

- 親ドキュメントへのリンク
- 計画一覧テーブル: 計画 / 対象 / 現状規模（**実測値**） / 主な問題 — 規模・優先度順に並べる
- 各計画の共通構成の 1 行説明と「全 PR 挙動不変・独立マージ可能」の原則
- **横断的な発見**: 単一の計画に属さない事項（dead code の疑い、feature 越境 import、既存の規約違反、テスト基盤の状態）を箇条書きで残す。ここは計画実行時の申し送りになるので省略しない

### 4. 最終報告

- 生成したファイルの一覧（絶対パス付き）。分析ファイル（一時ディレクトリ）は中間物であり、計画書に取り込み済みなので削除してよい旨を添える
- 対象ごとの規模と PR 本数、最も費用対効果が高い PR
- **要相談事項**: analyzer / writer が挙げた「実装前に判断が必要な分岐」を必ず転記する（勝手に決めない）
- 次のステップ: 計画のレビュー → 実行スキルでの PR 化

## 注意

- **読むだけ**。ソースコードもテストも変更しない。作るのは計画書と索引だけ
- **実測なしで書かない**。行数・回数・重複数は必ずコマンド出力を根拠にし、計測日を計画書に明記する
- 判断が割れる箇所（共通化の粒度、dead code の削除可否、逆流 import の解消方法）は計画書に**「実装前に相談」と書いて残す**。スキル側で結論を出さない
- ブランチ運用（main 直 / feature branch）はこのスキルでは決めない。実行スキル側でユーザーに確認する事項として計画書のリスク節に書く
- 対象がそもそも分割不要な規模（数百行で責務も混在していない）なら、計画書を作らずその旨を報告する
