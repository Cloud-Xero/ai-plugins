# 市場空白リサーチスキル

個人開発者・個人事業主が参入できる「市場の空白領域（ニッチ）」を、**構築期間別の3トラック（1日／1週間／1ヶ月）**の並列web調査で洗い出す。
トラックごとに market-researcher エージェントへ委譲し（＋反証役1本）、出典付きレポート群＋横断比較サマリをファイルに保存するところまでを一気通貫で行う。

## 設計思想（なぜこの形か）

- **構築期間で分けて並列に調べる**: 「AIフル活用で1日で作り切れるもの」「1週間」「1ヶ月」では、成立するプロダクトの形も課金モデルも売り方も全く違う。同じ調査に混ぜると大きい方に引きずられるため、トラックを分けて独立に探させる
- **評価軸を全トラックで固定する**: 「その期間内に本当に作り切れるか」「初月に目標額の売上が立つ経路があるか」を全プロンプトに埋め込むことで、トラックをまたいだ横断比較が可能になる
- **「不在の証明」に根拠を要求する**: 「空白と判断したら検索確認した根拠を書け」と指示することで、思い込みの空白（実は競合がいた）をエージェント自身が棄却できる
- **必ず反証役を1本混ぜる**: 案出し系の調査だけだと楽観に偏る。「その規模のプロダクトで本当に売上が立った実例はあるか」を批判的に検証する調査を並走させる

## 実行手順

### 1. 引数の解釈とチャネル制約の確認

`$ARGUMENTS` から以下を読み取る。なければデフォルトを使う:

| パラメータ | デフォルト | 例 |
|---|---|---|
| テーマ/観点 | なし（観点カタログから選定） | `介護業界` `法改正` `05,06,07` |
| **目標** | **リリース後1ヶ月以内に月5万円の売上** | `初月10万` |
| チャネル制約 | なし（**必ず最初に選択させる**） | `完全オンライン` `地域内オフラインOK` |

構築期間はパラメータではない。**常に「1日／1週間／1ヶ月」の3トラックを並列で調査する**（後述）。

- **目標は「リリース後1ヶ月以内に月5万円」の一本**。これを満たす見込みが立たない候補は、他の評価がどれだけ良くても**却下**として扱う。長期の成長性は評価軸にしない（初月に売上が立つ候補なら、その後の拡大は別途判断すればよい）
- この目標を通りやすいのは ①法定義務・期限など**既存の検索需要を即刈り取れるもの** ②**買い切り・スポット課金型**（見込み客ゼロからのサブスクは初月に件数が積めず不利） ③**ストア（アプリストア・マーケットプレイス）が集客を肩代わりするもの** ④**既に見込み客・オーディエンスに接点があるもの**

**チャネル制約の選択（必須・最初に行う）**: 引数で指定されていなければ、調査を始める前に AskUserQuestion で必ず選択させる:

- **A. 完全オンライン完結** — 集客・販売・提供・サポートの全てをオンラインで完結させたい。対面営業・訪問・提携行脚が必要な候補は除外する
- **B. 一部オフラインOK（居住地域内）** — 居住地域内で完結する対面接点（地元の商工会・業界団体・店舗訪問・提携営業など）なら許容する。この場合は**居住地域（都道府県・市区町村）も併せて確認**し、調査プロンプトに含める

チャネル制約は以降の全工程（プロンプト・サマリ評価軸）を貫く前提条件になる。

- 過去の調査結果（出力先ディレクトリ配下、特に `candidates.md`）があれば冒頭で確認し、既出の候補は各トラックのプロンプトに「既知の候補リスト（除外対象）」として埋め込む

### 2. 3トラックの定義

各トラックは「AIをフル活用する個人開発者」を前提に、その期間で**リリースまで到達できる**プロダクトの形を探す。

トラックの違いは**期間の制約だけ**であり、プロダクトの種類・領域・形式に制限はない。下表の例示はエージェントに規模感を伝えるためのキャリブレーションであって、**探索範囲の限定ではない**（例示にない形でも、期間内に販売開始まで到達できるなら何でも候補になる）。

| トラック | 規模感の例示（限定ではない） | 相性の良い課金モデルの例 |
|---|---|---|
| **1日** | 単機能webツール（変換・生成・診断・計算）、テンプレート/雛形のデジタル販売、プロンプト・スプレッドシート・Notionテンプレ等の情報財、既存過去問・公開データの整形物 | 買い切り（数百〜数千円）、投げ銭、広告 |
| **1週間** | 単機能SaaS/API（1エンドポイント）、ブラウザ拡張、ストア向けプラグイン（kintone/WordPress等）、ニッチ資格アプリ、CSV変換系ツール | 買い切り〜低額サブスク、ストア課金 |
| **1ヶ月** | 小規模SaaS（認証・課金・管理画面込み）、業務特化ツール（法定義務対応等）、複数機能のAPIサービス | サブスク、初期費用＋月額 |

注意: 「期間内に作り切れる」には、開発だけでなく**販売開始に必要な作業一式**（LP・決済・ストア審査等）を含める。ストア審査に2週間かかるものは1週間トラックでは成立しない。

### 3. 観点カタログ（各トラックに渡す切り口のヒント）

過去に実績のある切り口。トラックごとのプロンプトに「探し方のヒント」として一覧を添付する（テーマ指定がある場合はテーマを優先し、カタログは補助に回す）。

| # | 観点 | 空白の仮説 |
|---|---|---|
| 01 | 法改正・制度変更起点 | 新しい義務・事務負担が発生したのにツールが未整備 |
| 02 | 海外成立・日本未上陸 | 海外で収益実証済みだが日本語圏に競合がない |
| 03 | アナログ残存の縦型業界 | FAX/紙/Excel運用が残り、既存ツールが高すぎて中小に届かない |
| 05 | AIラッパーの収益化ニッチ | ChatGPT代替でも金を払う条件が成立する業務文書・フロー |
| 06 | 公共データ・オープンデータのAPI化 | 無料公開データの検索性・通知・API化が悪く実務者が困っている |
| 07 | サービス終了・値上げの受け皿 | 終了/改悪されたツールの移行先が乏しい |
| 08 | プラットフォーム内マーケットプレイス | ストア（kintone/WordPress/Notion等）内の日本業務慣行ニッチが空白 |
| 09 | 高齢化・事業承継・終活 | 承継実務の棚卸しが紙テンプレと高額コンサルの二極化 |
| 10 | インバウンド・民泊・飲食 | 小規模事業者の法定義務・多言語対応の実務が手作業 |
| 11 | ニッチ資格の学習ツール | 受験者1〜2万人規模の資格はアプリ供給が薄い |
| 12 | 既存SaaSの低評価レビュー起点 | 「機能過多で高い」不満への軽量代替が不在 |
| 13 | クリエイターエコノミーの裏方 | 収益集計・税務などの実害系業務だけ支払意欲がある |
| 14 | 法定点検・義務点検リマインド | 業者向けツールはあるがオーナー側の期限管理が空白 |

（04は反証役として常設のため欠番。予備観点の例: 移住・多拠点生活、ペット産業、越境EC、防災・BCP、外国人労働者の受け入れ実務、廃業・閉店の実務、など）

### 4. プロンプトの組み立て（トラック別×3＋反証役1）

トラックごとに以下のテンプレートで委譲プロンプトを作る。**不変部分は一字一句この規律を守る**（このスキルの品質の核）:

```
AIをフル活用する個人開発者が<トラック期間: 1日/1週間/1ヶ月>で「開発〜販売開始」まで
到達できる規模のプロダクトで、参入できる未整備または空白の市場を調査してください。

制約は期間だけです。プロダクトの種類・領域・形式は問いません。
規模感の例示（これに限定せず、期間内に販売開始できるなら何でも候補にすること）:
<トラック定義表の「規模感の例示」を転記>
相性の良い課金モデルの例: <同「相性の良い課金モデルの例」を転記>

<テーマ指定があればここに記載。なければ>探し方のヒント（これに限らず広く）:
<観点カタログの一覧を転記>

<既知の候補リストがあれば: 以下は調査済みの既知候補です。これらは除外し、新規のみ報告してください: ...>

必ず以下を守ること:
1. 収益額・価格・市場データは出典URL必須。自己申告のみの場合は「自己申告」と明記
2. 「空白/不在」と判断した場合は、実際に検索して確認した根拠を書く
3. **期間内に作り切れるか**を、開発だけでなく販売開始に必要な作業一式（LP・決済・
   ストア審査・コンテンツ制作）込みで評価する。審査や監修で期間を超えるものは却下
4. **初月売上の判定**を必須で行う: リリース後1ヶ月以内に月<目標額>の売上が見込めるか。
   初月の売上経路（既存検索需要の刈り取り / ストア流通 / 買い切り単価×見込み本数 /
   既存接点への直販 など）と単価×件数の内訳を具体的に示し、見込めない場合は
   その候補を「却下」と明記する。楽観シナリオではなく、類似事例の初月実績・
   検索ボリュームを根拠にすること
5. 各候補について**集客チャネルの評価**を必須で含める: 顧客は自分でオンライン検索して・
   試して・決済する層か（オンライン完結度: 高/中/低）。オフライン接点が事実上必須なら、
   その旨と必要な接点の種類を明記する
   <チャネル制約Aの場合に追記: オフライン営業が事実上必須と判断した候補は、
    その理由を明記した上で有望度を下げるか除外すること>
   <チャネル制約Bの場合に追記: オフライン接点は<居住地域>内で完結するものに限り許容。
    地域内で成立するか（対象顧客が地域内に十分いるか）も評価すること>
6. 憶測は「推測」と明記し、事実と区別する。調べ切れなかった論点は「未確認」として残す

最終出力は、後述の「出力フォーマット」に厳密に従い、有望度順に上位3〜5件を返してください。
フォーマット外の前置き・所感・繰り返しの説明は書かないでください。
```

### 4b. 出力フォーマット（固定・全トラック共通）

委譲プロンプトの末尾に以下のフォーマット指定を必ず含める。安定した横断比較と候補台帳の機械的な更新のため、**見出し・フィールド名は一字一句固定**とする:

```
# <トラック>調査レポート: <テーマ>
- 調査日: YYYY-MM-DD
- 条件: 構築<期間> / 初月<目標額> / <チャネル制約>

## 結論
（3行以内。最有望の候補と、その初月売上経路を一言で）

## 候補
### 候補1: <名前>（有望度: 高/中/低）
- **概要**: （1〜2文。何を・誰に・いくらで売るか）
- **空白の根拠**: （実際に検索して確認した内容。競合名と価格があれば記載）[出典]
- **需要の証拠**: （生の声・統計・収益実例など）[出典]
- **初月売上の判定**: 通過/却下 — 経路（検索刈り取り/ストア/買い切り/既存接点）、単価×件数=金額、根拠
- **課金モデル**: 買い切り/スポット/サブスク/広告 — 価格
- **構築**: 期間内の可否と、販売開始までに必要な作業（開発以外含む）
- **オンライン完結度**: 高/中/低 — 必要なオフライン接点があれば種類
- **リスク・未確認**: （法的リスク、推測に留まる点、要一次確認事項）

（候補2以降も同じ構造。各候補は400字以内を目安に簡潔に）

## 却下した候補
- <名前> — 却下理由（1行）

## 出典一覧
- [タイトル](URL)

## 未確認事項
- （箇条書き）
```

反証役の出力も同様に「## 結論 → ## 実例（事例名/売上額と裏付け度/初月までの経緯/事前オーディエンスの有無/出典）→ ## 共通パターン → ## 出典一覧 → ## 未確認事項」の固定構成を指定する。

**反証役（4本目・常設）**: 上記の代わりに以下を要求する:
「個人開発者が<1日/1週間/1ヶ月>規模で作った小さなプロダクトで、リリース初月から月<目標額>以上の売上を実際に立てた公開事例を日本・海外から収集し、共通パターン（何を・どこで・どう売ったか、事前のオーディエンスの有無）を検証してください。誇張された成功談と検証可能な事例を区別し、初月から売上が立つケースの前提条件を批判的に評価してください。」

### 5. 並列委譲

- 3トラック＋反証役の計4本を **market-researcher エージェント**に1メッセージでまとめて並列起動する
- 実行中は完了したトラックから順に一言サマリをユーザーに報告する（黙って待たない）

### 6. 保存

出力先（固定）: `/Users/xero/git/github.com/Cloud-Xero/obsidian-business/idea/market-research/<YYYYMMDD>/`
（ユーザーがその場で別の場所を明示した場合のみそちらを使う）

- 各トラックのレポート全文を保存: `1day_<テーマ>.md` / `1week_<テーマ>.md` / `1month_<テーマ>.md` / `verify_初月売上実例.md`（テーマ未指定なら `general`）
- エージェントの返答は**要約せず全文を保存**する（出典一覧・未確認事項を削らない）

### 7. 横断比較サマリの生成

全トラックの完了後、`00_サマリ.md` を作成（既存があれば追記）:

1. **前提となる調査結果** — 反証役の結論（初月から売上が立つケースの前提条件・再現性）と、今回の条件（目標・チャネル制約）を最初に書く
2. **トラック別の有望候補表** — 1日/1週間/1ヶ月のセクションに分け、各表の列: 候補 / 空白度 / 支払意欲の根拠 / **初月売上の経路と試算（単価×件数、根拠）** / 課金モデル / **オンライン完結度（高/中/低と必要なオフライン接点）**
   — 表は**目標（初月<目標額>）を満たす見込みのある候補のみ**を載せる。却下候補は3.に回す
3. **却下・参入すべきでないと確認された領域** — 理由付き（**初月売上の見込みが立たない**・期間内に作り切れない・法的リスク・レッドオーシャン・空白仮説の棄却・**チャネル制約との不適合**）。「時間をかければ有望」な却下候補は備考としてその旨を残す
4. **総合推奨** — トラック横断でどれから着手すべきか。1日トラックの候補で小さく売上を検証してから1週間/1ヶ月トラックに投資する、といった順序も提案する
5. **候補台帳の更新** — 出力先直下の `candidates.md`（`.../idea/market-research/candidates.md`）に今回の全候補（採用・却下とも）を固定形式で1行ずつ追記する（次回実行時の重複除外リストになる）:
   `- [YYYYMMDD][1day|1week|1month] <候補名> — <一言概要> — 通過/却下（理由）`

### 8. 報告

最終メッセージで以下を伝える:
- 保存先とファイル一覧
- トラック別の有望候補トップ（各1〜2文、初月売上の経路付き）
- 次のアクション候補（MVP仕様設計 / 競合価格の精査 / 一次情報の確認）

## 注意

- **出典のない数字を事実として書かない**。エージェントの返答に出典がない主張が混ざっていたらサマリに採用しない
- 「完全自動」「不労所得」系の期待には、反証役の調査結果を必ず添えて現実的な期待値を示す
- 法的リスクが確認された領域（例: 破産者情報の検索性向上、過去問の無断二次利用）は有望度に関わらず「参入禁止」として明示する
- 調査はあくまで二次情報ベース。着手判断の前には一次情報の確認（法令条文・主催団体への問い合わせ・当事者ヒアリング）を推奨事項として必ず残す
