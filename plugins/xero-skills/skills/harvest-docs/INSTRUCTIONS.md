# ドキュメント収穫スキル

カレントプロジェクト内の markdown ドキュメントを読み、[harvest スキル](../harvest/SKILL.md) の収穫ノートと同じフォーマットのノートを生成して保存する。
harvest が「セッション（会話）」を素材にするのに対し、このスキルは「既存のドキュメント」を素材にする。**抽出と保存だけを行い、後続処理には踏み込まない。**

## 手順

### 1. 出力先の解決

harvest スキルと同一。環境変数 `HARVEST_OUTPUT_DIR` のみを見る（`~/.claude/settings.json` の `env` で設定される）。

- 設定されていれば、そのディレクトリに保存する（ディレクトリが無ければ作成し、その旨を報告に含める）
- **未設定なら収穫を行わず停止し**、`~/.claude/settings.json` の `env` に `HARVEST_OUTPUT_DIR` を設定するようユーザーに促す。設定例:

  ```json
  { "env": { "HARVEST_OUTPUT_DIR": "/path/to/harvest" } }
  ```

  設定変更はセッション再起動後に反映される点も伝える

### 2. 対象ドキュメントの解決

- 引数でパスが指定されていれば、それを対象にする（ファイルなら単体、ディレクトリなら直下と配下の `.md` すべて）
- 引数が無ければ、カレントプロジェクトの `docs/` ディレクトリ配下の `.md` を再帰的に列挙する
  - `docs/` が無い場合は、プロジェクト内のドキュメント置き場らしきディレクトリ（`doc/`, `documents/` など）を探し、候補をユーザーに提示して確認する
- 対象が複数ある場合は、ファイル一覧を提示して「すべて収穫するか、一部を選ぶか」をユーザーに確認してから進める（無断で大量生成しない）

### 3. 抽出

対象ドキュメントごとに内容を読み、[note-template.md](../harvest/note-template.md) の観点で収穫ノートに再構成する。

- **ドキュメントに実際に書かれていることだけを書く**。行間を勝手に補完して事実のように書かない。ドキュメントから読み取れないことは省くか「原文に記載なし」と扱う
- テンプレートの観点（やったこと / 設計判断とその理由 / ハマり→解決 / 未解決・申し送り / 記事ネタになりそうな点）にドキュメントの内容を振り分ける。**該当が無いセクションは見出しごと省く**
- コード・コマンド・エラーメッセージは原文のままコードブロックで残す
- **ノート単体で読んで理解できる自己完結した文章にする**。元ドキュメントを読んでいない読者が前提知識なしで読めるよう、対象・背景をその場で明示する
- frontmatter は harvest と同じ構成で、以下だけ変える:
  - `source: harvest-docs`（固定。セッション由来ではなくドキュメント由来と識別するため）
  - `source_file:` に元ドキュメントのプロジェクトルートからの相対パスを記録する
  - `captured:` は実行日、`project:` はリポジトリ名、`tags:` は内容から付ける

### 4. 保存

- **1ソースドキュメント = 1ノート**。1つの md が複数トピックを含んでいてもファイルは分けず、セクションで区切る
- ファイル名: `yyyymmdd_{slug}.md`（slug はドキュメントの主題を表す短い英語。元ファイル名をそのまま使うのではなく内容に即したものにする）
- 同名ファイルが既にある場合は `-2` を付けて別ファイルにする（上書きしない）

### 5. 完了報告

- 生成したノートの保存先パス（複数あれば一覧）
- 各ノートの収穫ハイライト（設計判断・ハマり解決を中心に1〜2行）
- テンプレの「記事ネタになりそうな点」に書いた内容があれば一言添える

## 原則

- **捏造禁止**。ドキュメントに無い体験・数値・エラーメッセージを創作しない。収穫ノートの価値は一次情報であることにある
- 秘匿情報（APIキー・顧客名・社外秘の値）はノートに書き込まない。必要なら `<秘匿>` に置換する
- 元ドキュメントは変更しない（読み取り専用の素材として扱う）
